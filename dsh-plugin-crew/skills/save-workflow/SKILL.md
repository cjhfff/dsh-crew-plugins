# 保存或修改固定工作流

用户希望某类任务以后每次都按同一套步骤执行。你的工作是把它写成一份清晰、可直接照做的 SOP，并用 `workflow_save` 工具保存。保存后用户在对话框输入 `/名字` 就会按它执行。

## 判断是新建还是修改

- 用户说"保存""存成固定工作流"：根据**本次对话里实际做通的操作**整理（用过的命令、检查方法、踩过的坑和最终做法），不要凭空编造没验证过的步骤。
- 用户说"修改 xxx"：先用 skill 工具加载 `xxx`，拿到现有 SOP 正文（结果里也有文件路径），只改用户要求的部分，其余原样保留，然后保存完整新版本。旧版本会自动备份。
- 名字：小写英文加连字符（如 `selinux-from-logs`），简短、能看出用途。用户没给就你来起，并在结果里告诉他。

信息不足以写出可执行的步骤时（比如不知道日志从哪里来、交付到什么程度），只问最关键的一两个问题，其余按本次对话的做法写。

## SOP 正文格式（body 参数）

按下面的结构写，用用户的语言：

```
# <标题>

> 执行规则：严格按下列步骤顺序执行，不跳步、不合并步骤。开始时用 todo_write 列出全部步骤，每完成一步就更新。
> 必须偏离步骤时（环境不同、命令失败），先停下说明原因和替代做法，再继续。

## 适用场景
一两句：什么情况下用，什么情况下不要用。

## 开始前需要的输入
逐条列出（如：日志文件或粘贴内容、目标系统版本、模块名）。缺哪项就先向用户要，拿到再开始。

## 固定步骤
1. **步骤名** — 做什么。
   - 命令/脚本：`精确的命令`（有脚本就写 `scripts/xxx` 的调用方式）
   - 通过标准：怎样算这步完成；不满足时怎么办。
2. ...

## 检查与验证
最终要跑哪些检查、预期结果是什么。

## 禁止事项
明确列出不允许的做法（例如过宽的权限、未经确认修改生产环境）。

## 交付物
最后交给用户的东西和格式（文件名、摘要模板）。

## 失败与回滚
出错时怎么恢复。
```

## 脚本

能写成脚本的确定性步骤（解析日志、生成候选、格式检查等）写进 `files` 参数，例如 `{"scripts/parse-avc.sh": "..."}`，并在步骤里写明调用方式。脚本要在本次对话里验证过，或者明确标注"未验证"。只允许 `scripts/`、`references/`、`assets/` 下的文件；修改时如果不传 `files`，原有脚本保持不变。

## 保存

调用 `workflow_save`：`name`、`title`（中文短标题）、`description`（一句话：做什么、什么时候用）、`body`（上面的完整 SOP）、可选 `files`。默认只有用户输入 `/名字` 才会触发；用户明确希望 Leader 可以自动选用时才传 `modelInvocable: true`。

保存后用两三句话告诉用户：工作流名字和调用方式（`/名字`）、版本号、包含的步骤数和脚本，以及下次调用时需要准备什么输入。
